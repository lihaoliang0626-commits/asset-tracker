# 资产输入交互对比分析

## 1. 设计文档核心理念 vs 当前实现

### 设计文档方案
**5步向导式流程：**
```
新增资产
 → ① 选择资产大类（认知层）
    └─ 现金 | 投资资产 | 数字资产
 → ② 选择资产子类型（语义层）
    └─ 根据大类动态展示子类型
 → ③ 选择/新建账户（操作入口层，可跳过）
    └─ 账户是归属维度，不是资产类型
 → ④ 填写资产核心信息（事实层）
    └─ 唯一的数据填写页面
 → ⑤ 高级信息（折叠层，可选）
    └─ 成本价、标签、备注等
 → 完成确认
```

**核心设计原则：**
- **资产与账户分离**：Account是Asset的"归属维度"，不是资产类型
- **分层决策**：分类页只做选择，填写动作只在最终页
- **新手友好**：默认流程覆盖80%用户，高级字段全部折叠
- **允许不完美**：不要求成本价、不要求完整字段

### 当前实现方案
**单页面模态框：**
```
记录资产快照
 → 选择记录方式（快速/完整）
 → 直接添加资产
    └─ [+ 现金] [+ 银行账户] [+ 证券] [+ 加密资产] [+ 支付账户]
 → 在卡片中填写所有字段
 → 添加备注
 → 保存快照
```

**当前特点：**
- 单页面，所有操作在一个模态框完成
- 没有账户（Account）概念
- 字段平铺展示，没有分层
- 快速记录模式继承上次数据

---

## 2. 详细对比

| 维度 | 设计文档方案 | 当前实现 | 差异程度 |
|------|------------|---------|---------|
| **交互流程** | 5步向导式 | 单页面填写 | 🔴 大 |
| **信息架构** | Asset与Account分离 | 无Account概念 | 🔴 大 |
| **认知负荷** | 每步只回答一个问题 | 一次性面对所有字段 | 🟡 中 |
| **高级功能** | 折叠隐藏 | 平铺展示 | 🟢 小 |
| **新手引导** | 大卡片选择 → 逐步展开 | 直接操作按钮 | 🟡 中 |
| **数据模型** | 需要Account实体 | 仅Snapshot + AssetGroup | 🔴 大 |
| **灵活性** | 可跳过账户、允许不完整 | 已支持不完整记录 | 🟢 小 |

## 3. 关键差异分析

### 3.1 资产与账户的概念模型

**设计文档：**
```
用户心智："我在moomoo买了股票，在支付宝买了基金"
数据结构：
  Account (moomoo)
    └─ Asset (Stock: AAPL)
    └─ Asset (Stock: TSLA)
  Account (Alipay)
    └─ Asset (Fund: 易方达沪深300)
```

**当前实现：**
```
用户心智："我要记录我的股票和基金"
数据结构：
  Snapshot
    └─ AssetGroup (securities)
        └─ AssetItem (brokerName: "moomoo", ...)
        └─ AssetItem (brokerName: "IBKR", ...)
    └─ AssetGroup (payment)
        └─ AssetItem (paymentType: "alipay", ...)
```

**分析：**
- 设计文档强调"账户是入口"，符合真实心智
- 当前实现用字段（brokerName, paymentType）模拟账户
- 当前方案更轻量，但不支持账户级别的管理（如查看某个账户的所有资产）

### 3.2 分层决策 vs 一次性填写

**设计文档优势：**
- ✅ 降低认知负荷：每步只需思考一件事
- ✅ 减少选择焦虑：大卡片选择比下拉框更友好
- ✅ 清晰的进度感：用户知道"我在第几步"
- ✅ 容错友好：可以返回修改分类

**当前实现优势：**
- ✅ 操作效率高：熟练用户可以快速完成
- ✅ 开发成本低：单页面实现更简单
- ✅ 适合快照场景：资产记录是"记录时刻状态"，不是"管理资产库"

### 3.3 数据模型影响

**如果实施设计文档方案，需要引入：**
```typescript
// 新增Account实体
interface Account {
  id: string;
  userId: string;
  name: string;              // "moomoo"
  type: AccountType;         // "broker" | "bank" | "payment" | "wallet"
  platform?: string;         // 平台标识
  assets: Asset[];           // 该账户下的资产
  createdAt: number;
  updatedAt: number;
}

// Asset需要关联Account
interface Asset {
  id: string;
  accountId: string;         // 所属账户
  type: AssetType;
  // ... 其他字段
}
```

**数据迁移挑战：**
- 当前AssetItem中的 `brokerName`, `bankName`, `platform`, `paymentType` 需要转换为Account
- 需要数据迁移脚本

## 4. 实施建议

### 方案A：完全重构（高成本）
**适用场景：** 产品定位是"资产管理平台"（而非"资产快照工具"）

**实施步骤：**
1. 创建Account数据模型和存储层
2. 重构Snapshot数据结构，引入accountId
3. 实现5步向导UI组件
4. 数据迁移脚本
5. 兼容性测试

**工作量：** 约5-7天
**优势：** 符合用户心智，可扩展性强
**风险：** 破坏性变更，需要数据迁移

---

### 方案B：渐进式优化（推荐）
**适用场景：** 当前产品定位仍是"低频快照工具"

**Phase 1: 优化信息层次（1天）**
- 在当前模态框中增加分类选择卡片
- 将高级字段折叠（如成本价、标签）
- 优化字段标签和提示

**Phase 2: 引入账户概念（2天）**
- 添加Account实体（可选）
- 在添加资产时可选择已有账户
- 保持向后兼容（仍支持直接填写）

**Phase 3: 多步骤向导（可选）**
- 如果用户反馈需要，再考虑多步骤流程

**工作量：** Phase 1+2 约3天
**优势：** 低风险，渐进式改进
**风险：** 较低

---

### 方案C：保持现状（最低成本）
**适用场景：** 当前交互已满足需求，无明显用户痛点

**小优化建议：**
1. 在"添加资产"按钮区增加分类卡片引导
2. 折叠"汇率"等高级字段
3. 增加"上次使用的账户"快捷选择

**工作量：** 1天内
**优势：** 成本极低
**风险：** 无

---

## 5. 推荐决策

### 当前产品定位
根据PRD文档，本产品是**"低频、低负担、看清资产"**的快照工具，不是Mint/Kubera那样的综合资产管理平台。

### 推荐方案：**方案B（渐进式优化）**

**理由：**
1. **符合产品定位**：快照工具不需要复杂的账户管理
2. **平衡成本与收益**：小改进即可显著提升体验
3. **保持灵活性**：可根据用户反馈决定是否深化

**具体实施：**
- ✅ Phase 1: 优化信息层次（立即实施）
  - 折叠汇率等高级字段
  - 增加更清晰的分类引导

- ⏸️ Phase 2: 引入账户概念（观察需求）
  - 如果用户有"查看某个券商总资产"的需求再做

- ❌ Phase 3: 多步骤向导（暂不实施）
  - 对于低频快照场景，单页面效率更高

---

## 6. 设计文档的价值

虽然不建议完全实施设计文档方案，但其核心理念值得借鉴：

✅ **值得采纳：**
- 分层信息展示（核心字段 vs 高级字段）
- 允许不完美记录
- 清晰的字段标签和引导

❌ **暂不适用：**
- 资产与账户强分离（对快照工具过于复杂）
- 5步向导流程（降低快照记录效率）
- 完成确认页（增加操作步骤）

---

## 7. 后续行动

如果决定实施**方案B - Phase 1**，需要：

1. **优化字段层次** (0.5天)
   - 默认隐藏汇率字段（仅在非基准货币时展开）
   - 添加"高级选项"折叠区（成本价、标签等未来功能）

2. **优化添加资产引导** (0.5天)
   - 将按钮改为大卡片 + 图标
   - 增加类型说明文案

3. **优化表单布局** (0.5天)
   - 调整字段顺序（按重要性）
   - 优化输入框提示文案

**总工作量：** 约1.5天

---

**结论：** 设计文档提供了优秀的交互理念，但需结合产品定位和实际场景裁剪。建议采用渐进式优化策略，先改进信息层次和引导，暂不引入Account概念和多步骤流程。
